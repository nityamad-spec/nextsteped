## Why duplicates are happening

In `supabase/functions/generate-weekly-quiz/index.ts`:

1. **No cross-tier dedupe.** The dedupe check at lines 265–266 (`accepted.some(...)`) only compares against questions **within the same tier**. Each tier (standard / easy / medium / hard) is generated by an independent call to `generateTier`, run in parallel via `Promise.allSettled` (line 416). Nothing prevents the standard tier and the medium tier from producing the same stem.
2. **Standard and medium are functionally identical to the model.** Both tiers use `difficulty: 0.5` (lines 26 & 28), the same Bloom guidance ("mostly 2-3, at least 40% bloom 3"), the same concept list, same week, same model, same temperature (0.35). Given identical inputs and a low temperature, Gemini tends to converge on the same "obvious" question per concept, so standard ↔ medium collisions are expected. Easy can also collide with standard/medium when the model picks a basic concept that fits both.
3. **Parallel generation = no shared "already-asked" memory.** Because all four tiers fire at the same time, even if we added a post-hoc filter, the model never sees what the other tiers produced, so it can't avoid them at generation time.
4. **Loose dedupe key.** The within-tier key is `content_text.slice(0,120).toLowerCase()` — a one-word edit ("Which" → "What") makes two near-identical stems pass as distinct.

## Fix

### 1. Differentiate standard vs medium

- Keep standard at `difficulty: 0.5` but reframe it as the **shared, canonical** quiz everyone takes — Bloom target mostly 2 (Understand) with a couple of bloom-3 items. Lower its target slightly (e.g. `0.45`).
- Push medium to `difficulty: 0.6` with Bloom target mostly 3 (Apply), so the model has a real reason to write a different question.
- Easy stays at `0.2` (Bloom 1–2); hard stays at `0.85` (Bloom 3–4).

### 2. Generate sequentially with cross-tier exclusion list

Replace the `Promise.allSettled` parallel fan-out with a sequential pipeline in this order: **standard → easy → medium → hard**. After each tier finishes, pass the list of already-accepted stems into the next tier's prompt as an explicit "AVOID — these stems were already used this week, write something materially different" block, and also use them to seed the local dedupe set.

Trade-off: sequential generation is slower. To stay within the 130s global deadline, reduce per-tier `maxAttempts` from 3–4 to 2, and shrink `batchSize` only if needed. Tiers that fail still salvage partial results (current behavior preserved).

### 3. Stronger dedupe key

Replace the 120-char prefix key with a normalized fingerprint:

- lowercase, strip punctuation, collapse whitespace, drop common stop-words and question openers ("which", "what", "is", "the", "of", "a", "an", etc.)
- take the **sorted set** of remaining tokens, join, hash
- two questions whose normalized token-sets overlap by >70% are also treated as duplicates (Jaccard similarity), not just exact-key collisions

Apply this both inside a tier and across tiers via the shared exclusion set.

### 4. Slightly higher temperature on adaptive tiers

Bump temperature from `0.35` to `0.5` for easy/medium/hard (keep `0.35` for standard so it stays stable). Lower-temperature sampling on the same prompt is one of the main reasons the model returns near-identical stems.

## Files to change

- `supabase/functions/generate-weekly-quiz/index.ts` — all of the above. No DB schema, no UI, no other edge functions touched.
